Dockerfiles & Compose

Every instruction, every service, graded

GreenSecOps reads your Dockerfiles and Compose files together — a Compose file and its override are merged before grading — and scores them across four categories.

Security
  • Containers that run as root because no USER was ever set
  • Privileged services, added SYS_ADMIN, host PID/IPC namespaces, and mounted Docker sockets
  • Credentials baked into a build arg or hardcoded in Compose
  • curl … | sh installers and downloads with TLS verification switched off
  • Database ports published on every interface instead of loopback
  • An override file that quietly undoes the base file's hardening
Reliability
  • Base images pinned to a floating tag rather than a digest
  • Missing HEALTHCHECK, and dependencies waited on without a health condition
  • Shell-form ENTRYPOINT that swallows shutdown signals
  • Services with no restart policy
  • Images with no CMD or ENTRYPOINT at all
Energy
  • Single-stage builds shipping a whole toolchain to production
  • Heavy base images where a slim variant would do
  • COPY . before the dependency install, busting the layer cache on every source change
  • apt and pip caches left behind in the final image
  • Services with no CPU or memory limits, and unbounded log files
Maintainability
  • Missing WORKDIR, leaving paths to guesswork
  • Missing OCI labels, so an image can't be traced back to its source
  • The deprecated MAINTAINER instruction
  • The obsolete Compose version: key
How It Works

Nothing to configure

Container files are recognisable by name, so GreenSecOps finds them itself. There is no folder to register and no manifest to keep current.

1
Install the GitHub App

Your repository is registered for container analysis automatically, from the root down. Monorepos can add extra targets to have each sub-project graded separately.

2
Graded on every push

Dockerfile, Dockerfile.*, *.Dockerfile, Containerfile, compose.yml and docker-compose*.yml are all picked up. A Compose file and its override are merged first, which is the only way to see that an override removed a setting rather than never having had one.

3
Fix it in a pull request

Review each finding with remediation guidance, generate an AI fix, and ship every rewritten file as a single pull request — comments, stage names and indentation preserved.

Docker Runtime

Fixes informed by what the container actually did

Static analysis reads the file. The companion GitHub Action measures the build and the running container — and those measurements are handed to the fix generator as facts, so a memory limit comes from an observed peak rather than a round guess.

What went wrong
  • Containers killed by the OOM killer, or running close to their limit
  • Restart loops and non-zero exits
  • Health checks that never turned healthy
  • A memory limit that doesn't match what the container needs
What it cost you
  • CPU throttling against the configured quota
  • Slow image builds, with the time attributed
  • Layer caching that isn't actually working — measured hit ratio, not a guess from the file
What you shipped
  • Oversized images, and the single layer responsible
  • Bloated build contexts uploaded to the daemon on every build
  • Excessive layer counts
1
Add the telemetry action

Drop the GreenSecOps Telemetry action into the workflow that builds your image. It samples the build and the containers it starts, in the background, while your job runs.

2
Point it at the Dockerfile

Pass dockerfile_path — that's the join back to the static analysis — and a docker buildx build --metadata-file JSON if you have one. Cache-hit data, the most useful build metric, is only available from that metadata.

3
Measurements feed the fix

The observed facts arrive alongside the static findings when you generate a fix — kept deliberately separate, because a finding says the file is wrong while a measurement says what the container did.
