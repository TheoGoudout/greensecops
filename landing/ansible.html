Ansible

Every task, read the way an attacker would

Point GreenSecOps at any folder in your repo — a flat playbook directory, a full roles/ tree, or the whole repository — and every playbook, task file, handler, variables file and requirements.yml is graded across four categories.

Security
  • Shell commands interpolating variables without | quote
  • Credentials written literally into variables files
  • Tasks handling secrets without no_log, leaking them into logs
  • TLS verification disabled with validate_certs: false
  • World-writable file and directory modes
Reliability
  • Remote downloads with no checksum to verify what arrived
  • Galaxy collections and roles pinned to no version
  • ignore_errors: true hiding real failures
  • Services started but never enabled, so they vanish on reboot
  • command and shell tasks with no changed_when
Energy
  • Packages pinned to state: latest, re-resolving on every run
  • Package modules called in a loop instead of once with a list
  • git checkouts with no version, refetching each time
  • Apt caches updated on every play
Maintainability
  • Unnamed tasks, unreadable in output and unreachable by --start-at-task
How It Works

No inventory, no dry run, no SSH

GreenSecOps analyses your Ansible source directly. It never connects to a host, never needs an inventory, and never runs a play in check mode to grade it.

1
Point it at your Ansible

Register the directory that holds your playbooks and roles — or the repository root, since an Ansible project often is the whole repo. Files are recognised by shape, not by path, so an inventory or a Compose file living alongside them is left alone.

2
Graded on every push

Each push parses your YAML — flattening block, rescue and always so an inherited no_log counts — and runs the shared Rego rule catalog, returning per-category grades in seconds.

3
Fix it in a pull request

Review each finding against the task it fired on, generate an AI fix, and open a pull request. Every rewrite is checked to have kept each Jinja variable and every !vault tag it started with — so a fix can never quietly change what a play does.

See It In Action

From unverified download to pinned and quiet

A task that fetches a binary over the network with nothing to verify it, and logs a registry password while it works — and the same task after its AI-generated fix.

Before
roles/docker/tasks/main.yml
- name: Install the Compose plugin ansible.builtin.get_url: url: "{{ compose_url }}" dest: "/usr/libexec/docker/cli-plugins/docker-compose" mode: "0755" - name: Log in to the registry ansible.builtin.shell: cmd: "docker login -u AWS {{ registry }}"
D Unverified download, unquoted
interpolation, no changed_when,
credential logged in the clear
AI-generated fix
After
roles/docker/tasks/main.yml
- name: Install the Compose plugin ansible.builtin.get_url: url: "{{ compose_url }}" dest: "/usr/libexec/docker/cli-plugins/docker-compose" mode: "0755" checksum: "sha256:{{ compose_sha256[arch] }}" - name: Log in to the registry ansible.builtin.shell: cmd: "docker login -u AWS {{ registry | quote }}" changed_when: false no_log: true
A+++ Binary pinned to a digest, input
quoted, honest changed state,
credential kept out of the log
