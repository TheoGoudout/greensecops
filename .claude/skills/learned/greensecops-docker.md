# GreenSecOps: Docker Compose Lifecycle

**When to use:** Starting the dev stack, building images, running CI-like tests, or deploying.

## Dev (hot reload)

```bash
docker compose watch
# Merges compose.yml + compose.override.yml automatically
# Hot reloads: backend (sync), frontend (sync), celery-worker (sync+restart)
# Rebuilds on: pyproject.toml, uv.lock, package.json, bun.lock changes
```

## Useful individual commands

```bash
# Start only specific services (useful to run backend/frontend locally instead)
docker compose up -d db redis mailcatcher
docker compose up -d db redis mailcatcher opa

# Stop one service so you can run it locally
docker compose stop frontend
docker compose stop backend

# View logs
docker compose logs -f
docker compose logs -f backend
docker compose logs -f celery-worker

# Restart a service
docker compose restart backend
```

## Production build (no override file)

```bash
docker compose -f compose.yml build
docker compose -f compose.yml up -d
```

## Test docker compose health (CI equivalent)

```bash
cp .env.example .env && cp frontend/.env.example frontend/.env
docker compose -f compose.yml build
docker compose -f compose.yml down -v --remove-orphans
docker compose -f compose.yml up -d --wait backend frontend
docker compose -f compose.yml down -v --remove-orphans
```

## Clean teardown

```bash
docker compose down -v --remove-orphans
# -v removes named volumes (app-db-data, app-redis-data) — resets DB
# --remove-orphans removes containers from removed services
```

**Warning:** `-v` destroys all DB data. Omit `-v` to keep data between restarts.

## Service dependency graph

```
prestart (one-shot) ← db (healthy)
backend ← db (healthy) + redis (healthy) + prestart (completed)
celery-worker ← db (healthy) + redis (healthy) + prestart (completed)
celery-beat ← redis (healthy) + prestart (completed)
flower ← redis
frontend ← (none)
opa ← (none, mounts ./backend/app/rules as read-only)
```

## Coolify env vars (important for CI)

`compose.yml` uses Coolify-injected variable names — these are normally auto-generated by Coolify at deploy time:
- `SERVICE_USER_POSTGRES` → Postgres user
- `SERVICE_PASSWORD_POSTGRES` → Postgres password
- `SERVICE_PASSWORD_64_SECRETKEY` → app secret key (64 chars)
- `SERVICE_PASSWORD_FIRSTSUPERUSER` → first superuser password
- `SERVICE_FQDN_BACKEND` / `SERVICE_FQDN_FRONTEND` → service FQDNs

`compose.override.yml` maps plain `POSTGRES_USER`, `POSTGRES_PASSWORD`, `SECRET_KEY` for local dev.

CI sets these as workflow env vars with test values. Both `.env` and `frontend/.env` must exist before running compose.

## Reset and rebuild from scratch

```bash
docker compose down -v --remove-orphans
docker compose build --no-cache
docker compose watch
```
